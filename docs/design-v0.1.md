# Green 设计文档

版本 v0.1 · 2026-11-26 · 状态：待批准
范围：仅调研与设计，不含产品代码。实测数据来自 `research/bench`（本机 Windows，可复跑）。

---

## 0. 摘要

Green 是一个内容优先、可插拔的全能文档编辑器：内置 Word / PDF / PPT / Excel，插件市场提供格式、视图与增强能力。

**核心结论：架构选「单壳多引擎」（A 与 B 的混合），不选纯 A，也不选纯 B。**

- 对用户：一个应用、一个窗口、一条工具条；打开任何格式，正文区换的是「表面」（surface），不是应用。
- 对工程：每种格式的引擎跑在独立 worker 进程里，崩溃、卡顿、内存互不牵连；外壳与插件只依赖一层窄接口。
- 依据：LibreOffice 是「单进程多模块」，启动与构建成本被病程拖累；WPS 是把多组件与整合窗口做成用户可切的两种模式；ONLYOFFICE 是「独立转换器 + 每格式一套编辑器」；ElyOffice 是「8 个二进制 + 共享外壳 crate + 独立 worker」。四者没有一个是纯 B，也没有一个把引擎塞进 UI 进程。

**性能结论：5 万字 Markdown 的瓶颈不在解析，也不在文本缓冲，而在排版与启动。** 实测（50,130 字符、348 块）：

| 环节 | 实测中位 | 结论 |
| --- | --- | --- |
| pulldown-cmark 全量解析 | 0.11 ms | 解析可以每次全量做 |
| ropey 单字符插入 p99 | 0.0025 ms | 文本缓冲不是问题 |
| cosmic-text 整篇一个 buffer 排版 | 185–197 ms | 朴素做法不可接受 |
| cosmic-text 按块排版（348 块） | 104–108 ms（中位 0.35 ms/块） | 后台可接受，且可增量 |
| 单块重排 | 0.35 ms | 键入时只付这一块 |
| 首屏（填满 1200px，12 块） | 3.5 ms | 首屏排版不是瓶颈 |
| 字体枚举 FontSystem::new | 180–195 ms / 次 | 冷启动的大头，必须缓存索引 |
| 16 线程各自 FontSystem 并行排版 | 823–946 ms | 比单线程慢 7.6–9 倍，不要天真并行 |

**成本结论：最贵的一项不是写代码，是 LibreOffice 内核。** ElyOffice 为此维护 142 个 LibreOffice 补丁（编号至 0149）、约 1 小时的内核构建、以及一套「命令白名单」桥接层。选它，等于选了一条长期维护上游补丁的路线。

## 1. 需求与约束

### 1.1 原始需求（作为验收基线）

1. 内置 Word、PDF、PPT、Excel 四种格式。
2. 插件市场：可按需安装 Markdown、Git tree 等格式/视图插件，以及「更好的 Excel 支持」这类增强插件。
3. UI 参考 ima 笔记模式：单栏、顶部极简工具条、正文居中占满、无侧栏无 tab。
4. 5 万字 Markdown 不卡顿，且指标可测。
5. Rust 为主，其他语言模块化组合；基座参考 ElyOffice。
6. 先 Windows。

### 1.2 我在设计里补的硬约束

这些不是新需求，是把需求翻译成工程可执行的东西：

- **C1 保真优先于自研**：Word/Excel/PPT 的排版结果必须与 Microsoft Office 可对照；不能出现「我们自己觉得对」的版式。
- **C2 引擎可替换**：任一格式引擎必须能在不改外壳的前提下被换掉（这是插件市场的前提）。
- **C3 崩溃不丢稿**：引擎进程崩溃时，用户已输入的内容必须可恢复。
- **C4 单一事实来源**：任何格式在磁盘上的字节，与内存中的模型之间只有一条有损边界；不允许「块树 ↔ Markdown」双向转换这种会改写原文的设计。
- **C5 许可可见**：GPL/AGPL 依赖必须在文档与安装包里明示，且不得意外传染到自有代码。
- **C6 首屏与输入延迟分开度量**：打开慢和打字卡是两个问题，不能用一个「流畅」掩盖。

### 1.3 明确不做（v1）

- 不做协同编辑（CRDT/OT）；架构留出接口，不实现。
- 不做云盘、账号体系。
- 不做 PDF 正文重排式编辑（见 §8.5 与决策 D3）。
- 不做 macOS/Linux 发布，但代码不写死 Win32。

## 2. 同类项目调研

调研原则：只看公开可核实的事实（源码结构、官方文档、白皮书、发布说明）。凡是我推断的，文中标「判断」。

### 2.1 LibreOffice：组件模型与 UNO

**事实**

- 一个 `soffice` 进程承载全部文档类型；Writer / Calc / Impress 是同一代码库里的模块（`sw` / `sc` / `sd`），由 `desktop` 模块创建 frame 并加载文档模型。
- UNO 是自研组件模型：IDL 定义接口，语言无关的二进制类型布局，跨进程/跨网络用 bridge；启动时建立 service manager 与 type manager，组件通过 `XInterface::queryInterface` 取接口。
- 组件通过 `unopkg` 注册，扩展可挂菜单/工具栏。

**取舍与代价**

- 优点：模型统一，`XText`/`XSheet` 这类接口让宏、扩展、外部自动化（JODConverter、unoconv）都能复用；跨语言绑定齐全。
- 代价：为了「语言无关 + 跨进程」，引入了完整的一套类型系统、注册表、桥接层。这套东西的维护成本最终体现在启动时间、构建复杂度和新人上手成本上。ElyOffice 的选择很说明问题：它用 LibreOfficeKit（免 UNO 远程调用的进程内 C API），界面只允许发**UNO 命令字符串**（`ely_lok::commands::COMMANDS`），而不是暴露整个 UNO 对象模型——这等于承认「UNO 的表达力」对宿主应用是负担。
- **判断**：Green 不应复制 UNO。需要的是「一层窄的、可版本化的文档接口」，不是通用组件总线。

### 2.2 ONLYOFFICE：x2t 与三套编辑器

**事实**

- 仓库分 `core`（原生转换器，含 `X2tConverter/`、`OOXML/`、`OdfFile/`、`MsBinaryFile/`、`PdfFile/` 等按格式分的目录）、`sdkjs`（JS SDK）、`web-apps`（前端）、`server`。
- `core` 负责 DOC/DOCX/ODT/RTF/PDF/XLS/XLSX/PPT/PPTX 等格式之间的转换，编辑器消费其内部格式；三个编辑器是三套 JS 应用，共用一套前端框架。
- 许可：DocumentServer 与 core 均为 AGPL-3.0。

**取舍与代价**

- 可借鉴：**把「格式转换」从「编辑」里拆出去，做成独立原生进程**。转换失败、转换器崩溃，不会带走编辑器；转换器也不必知道 UI。
- 可借鉴：**内部统一文档模型 + 每格式一个 codec**。这比「每个格式一套独立模型」更容易做跨格式粘贴与导出。
- 不可借鉴：渲染跑在浏览器 canvas 里。桌面端要嵌一个 CEF/WebView2 才能复用，与「Rust 为主、原生性能」冲突，且 LOK canvas 那类输入/无障碍问题会以另一种形式重现。
- **判断**：Green 采用「独立转换器进程 + 统一模型」的思想，但表面用原生渲染；不采用 AGPL 代码。

### 2.3 WPS：四层柔性架构与两种窗口模式

**事实（来自 WPS 官方白皮书与操作指引）**

- 四层架构：系统层（跨平台系统接口）→ 公用层（共享功能模块，官方称整个体系「仅 300 多 Mb」）→ 核心层（文字排版、表格计算、演示动画、图形/图表/界面引擎）→ 应用层（WPS 文字 / 表格 / 演示 / 控件 / 插件，以及第三方插件与控件）。
- 窗口管理有两种模式，用户在设置里切换并重启生效：
  - **多组件模式**：文字、表格、演示、PDF 各自独立窗口，桌面生成四个图标；
  - **整合模式**：多种文档的标签聚合进同一窗口，桌面只有一个图标，支持标签拆分/组合与「工作区」。
- 插件（加载项）基于 Web 技术：`ribbon.xml` 定义功能区，`main.js`/网页承载逻辑，底层是 Chromium；安装靠 `publish.xml`；从 12.1.0.16910 起，通过改 `oem.ini` 加载的方式被安全策略限制。
- 二次开发接口同时提供 `msoAPI` 与 `ksoAPI` 两套命名空间，目标是让 Office 的 VBA/COM 代码少改。

**取舍与代价**

- 这是**最直接支持混合方案的证据**：同一套引擎、同一套代码，窗口层可以「分」也可以「合」，而且做成用户可选项。说明「多组件」与「单窗口」不是架构二选一，而是外壳策略。
- 「四层」把「跨平台系统接口」「共享模块」「格式引擎」「应用组件」分开，正是 Green 想要的边界。
- 代价：WPS 为了兼容 Office，把接口、快捷键、甚至对象模型都做成对方的形状；这是一条以兼容换市场的路线，Green 在 v1 不需要承担同等兼容负担（但要承担「打开不跑版」的负担）。
- **判断**：Green 采用 WPS 的分层，但**不**提供两种窗口模式。产品定位是内容优先，多组件模式会让用户回到「先选应用」的心智，与需求 3 冲突。

### 2.4 ElyOffice：基座参考

**事实**：来自仓库 `agents.md`、`README.md`、`docs/licenses.md`、`docs/compatibility.md`。

- 8 个应用各自一个二进制：ElyDoc/ElyTable/ElyShow（LibreOfficeKit）、ElyPDF（MuPDF + Tesseract）、ElyMail、ElyTree（Git CLI）、ElyMark（Markdown 自研）、ElyAgent。
- crate 边界：`ely-ui`、`ely-platform`、`ely-ipc`（应用与 worker 之间的帧与停止）、`ely-files`、`ely-lok`（LOK 图块画布与输入桥）、`ely-office`（文档应用共用的外壳）、`ely-pdf-engine`、`ely-pdf-worker`（只有它编 MuPDF）、`ely-mail-engine`、`ely-start`、`ely-login`。
- 引擎在工作进程里；应用与 worker 只经本用户端点相连（Windows 命名管道，macOS/Linux 0600 套接字），握手核对版本与内核编号。
- 界面只经命令白名单发 UNO 命令；内核弹出的对话框即刻关闭并报错，需要的由 Ely 自建；内核改动只以补丁序列进入（LibreOffice 26.2.6.3 + 142 个补丁、编号至 0149；MuPDF 1.28.5 + 11 个；gpui + 15 个）。
- 每个应用只跑一份，再次启动把文件交给运行中的那份；文档应用可开多窗口，共用一个引擎。
- 发布：一个平台一个安装包，Doc/Table/Show 共用一份内核；登录后常驻一个已自检的空闲引擎（不给开关，按物理内存少留或不留）。
- 更新：整包一致更新，清单 ed25519 签名，缺签名即拒；自动检查默认关，从不静默安装。
- 性能立场：八个应用都不许卡顿（120 FPS 手感，「potato computer」也要流畅），界面线程不等内核、不持 worker 锁，空闲不做事。
- 实测（其 `docs/compatibility.md`）：Windows 上 ElyDoc 打开 `big.docx` 中位 1.10 s，Word 同为 1.10 s；ElyShow 打开 19 MB 演示稿 1.58 s，PowerPoint 1.09 s。ElyPDF 曾出现首次启动 10.9 s（未复现），常态 3.4–3.6 s。
- 缺口自述里有几条对 Green 直接有用：LOK 图块画布与输入桥要自建；gpui 无 HTML 剪贴板（用 arboard）；LOK 无障碍只报当前段落（要打补丁）；行内公式在 gpui 文本里放不了图片；PPTX 章节缺失；表格公式栏与名称框自建。
- 许可：自有代码 MIT；LibreOffice MPL-2.0 等；MuPDF AGPL-3.0（因此 ElyPDF 的发行包整体须按 AGPL 履行）；Git GPL-2.0。

**取舍与代价**

- 这是与 Green 目标最接近的公开工程实证：Rust + GPUI + LOK 在 Windows 上可行，且已经解决过「图块画布、输入桥、对象手柄、命令白名单」这些脏活。
- 但它是**多应用**的：用户要选 ElyDoc 还是 ElyTable。它用「一个安装包 + 共用内核 + 文件关联不抢默认」把体验缝合起来，仍然没有做到「打开任何文件都是同一个应用」。
- 它把 PDF 押在 MuPDF（AGPL）上，这是 Green 必须避开的许可约束（见 D3）。
- **判断**：Green 借鉴其进程隔离、命令白名单、补丁纪律、整包更新与常驻引擎；在应用形态上改为单壳，在 PDF 引擎上改为 pdfium。

### 2.5 内容型编辑器：Notion / Typora / Obsidian / ima

**事实**

- **Notion**：一切皆 block，block 有 id/type/properties/parent/version；编辑产生 op，op 组成 transaction，本地 RecordCache + TransactionQueue，服务端提交后经 WebSocket 推送。内容权威是块数据，Markdown 只在导入导出时转换。
- **Obsidian**：编辑器底层 CodeMirror 6，编辑的是 Markdown 原文，实时预览是在源码上渲染；另有源码模式与阅读模式。
- **Typora**：所见即所得，另有源码模式；编辑器内核未公开。其产品主张是「去掉预览窗口、模式切换与语法符号」。
- **MarkText / Joplin 一类**：富文本 + 源码两套编辑器，保存时用 Markdown 序列化/反序列化，社区已明确指出这类往返会改写原文（`*` 与 `_`、列表符号、有序编号、转义）。
- **ima**：应用外壳有左侧导航（知识库/笔记）与搜索首页；「新建笔记」页是一个类似 Word/腾讯文档的完整编辑器，支持 Markdown 语法、`/` 唤起 AI、选中后扩写/缩写/翻译。**注意：ima 的外壳有侧栏，Green 只参考它的「笔记页」，不参考外壳。**
- 第三方对 Markdown 编辑器 UI 的横向调研结论（colophon 项目 2026-07 文档）：极简单栏是「简洁好看」阵营的主流形态；「功能强但界面密」的产品口碑天花板被直接压住；单栏成立的前提是「逐段实时渲染消灭预览栏」。

**取舍与代价**

- 块模型（Notion）让虚拟化、权限继承、协同都变简单，但把「原文保真」牺牲掉了。对 Green 的 Markdown 插件来说这是不可接受的：用户的 `.md` 在 Git 里，改一个字不该产生满屏 diff。
- 源码为权威（Obsidian/ElyMark）保真，但「所见即所得」要做到位需要逐段渲染 + 语法符号按需显隐，工程量在渲染层。
- **判断**：Markdown 采用「源码为权威 + 块索引 + 逐段渲染」；DOCX/XLSX/PPTX 采用「格式模型为权威」，因为它们的权威本来就是 OOXML，不存在二次序列化损失。

### 2.6 横向对比

| 项目 | 文档模型权威 | 引擎位置 | 外壳形态 | 跨格式 | 许可 |
| --- | --- | --- | --- | --- | --- |
| LibreOffice | 自有模型（ODF 为中心） | 同进程模块 | 单进程多 frame | 强（内部转换） | MPL-2.0 |
| ONLYOFFICE | 内部 bin | 独立 x2t 进程 + JS 编辑器 | Web 应用 | 强（转换器） | AGPL-3.0 |

## 3. 可借鉴的原则

每条给出来源、结论、以及我为什么这么判断。

### P1 单一事实来源，且是有损边界最少的那一个

**来源**：Obsidian（Markdown 原文）vs MarkText/Joplin（块树与 Markdown 双向往返导致原文被改写）。
**结论**：Markdown 的权威是原文；DOCX/XLSX/PPTX 的权威是 OOXML 包；PDF 的权威是 PDF 对象图。内存模型可以是任何形状，但写入磁盘时必须能证明「没改的地方字节没变」。
**判断**：这条决定了插件 API 的形状——格式插件拿到的是**字节**，返回的是**视图模型**，而不是让宿主把文档转成通用 JSON 再转回去。

### P2 内容即界面，chrome 按需出现

**来源**：Typora（去掉预览栏与模式切换）、iA Writer/Apostrophe（零面板）、colophon 横向调研（界面密度与口碑负相关）、ima 笔记页。
**结论**：常驻 chrome 只有一条工具条；侧栏、面板、缩略图都必须是「按需浮层」，不能占常驻宽度。
**判断**：需求 3 不是审美偏好，是留存指标。但它有一个硬边界：**电子表格的网格、幻灯片的画布、PDF 的页面本身就是内容**，它们的内部导航（工作表标签、幻灯片条、页码）不算 chrome。这条边界必须在产品上明确，否则「无侧栏」会被解释成「不能有工作表标签」。

### P3 引擎与外壳分离，引擎可替换

**来源**：WPS 四层架构、ONLYOFFICE core/sdkjs 分离、ElyOffice 的 `ely-office` 外壳 crate + 各 worker。
**结论**：外壳只依赖一个 `DocumentHost` 接口；引擎通过进程边界与协议版本接入。
**判断**：插件市场要能替换「更好的 Excel」，前提就是引擎可换。若外壳直接调 LOK，这个需求永远做不成。

### P4 进程隔离，而不是线程隔离

**来源**：ElyOffice worker + 命名管道 + 版本握手；LibreOffice 单进程启动慢且一处崩溃全崩。
**结论**：LOK、pdfium 各跑在独立进程；宿主只持有句柄与帧。
**判断**：这不是「更安全」的口号。LOK 会阻塞、会弹自己的对话框、会吃几个 GB 内存；pdfium 官方假定非线程安全，`pdfium-render` 直接在全局部加互斥锁。放在 UI 进程里，任何一次长操作都会变成界面卡死。

### P5 命令白名单优于完整 API 暴露

**来源**：ElyOffice「界面只经 `ely_lok::commands::COMMANDS` 发 UNO 命令」。
**结论**：外壳与引擎之间的写操作集合是一个封闭枚举，不是对象图。
**判断**：白名单可以版本化、可以审计、可以给插件做权限映射（「这个插件只能发这 30 条命令」）。暴露 UNO 对象图则相反：任何插件都能拿到任意能力，权限模型直接失效。

### P6 转换器独立成进程

**来源**：ONLYOFFICE x2t。
**结论**：导入、导出、另存为、批量转换走独立 worker，可被杀、可超时、可并行。
**判断**：格式转换是最容易崩溃、最容易被恶意文件攻击的环节，也是唯一可以「失败就重试」的环节。把它和编辑会话解耦，收益远大于成本。

### P7 增量要按「块」切，但重排要能收敛

**来源**：CodeMirror 6 的视口外虚拟化与按视口增量解析；ProseMirror 默认不虚拟化导致大文档必须自建懒渲染；本项目的实测（§9）。
**结论**：块的边界用于**失效传播**，行的边界用于**重排计算**；编辑一行后向下重排，直到断行位置与纵坐标重新与旧结果一致（收敛）才停止。
**判断**：只做「块级脏标记」在单段 5 万字时会失效（整段重排）；只做「行级收敛」在块结构变化（插入表格）时不够。两者必须都有。

### P8 并行不是免费午餐

**来源**：本项目实测：16 个 FontSystem 各自排版 348 块耗时 823–946 ms，单线程 104–108 ms（两次运行）。
**结论**：排版默认单线程 + 后台线程；只有共享字体/字形缓存之后才考虑并行。
**判断**：每个 `FontSystem` 独立做字体枚举与字形缓存，冷启动成本（180 ms/个）与缓存重复直接把并行收益吃掉。这条推翻了「多线程排版一定更快」的直觉，必须写进设计，否则实现阶段会重犯。

### P9 更新整包一致，清单签名

**来源**：ElyOffice（整包更新、ed25519 清单、缺失即拒、从不静默安装）。
**结论**：host、worker、内置插件同版本发布；更新清单签名；自动检查默认关。
**判断**：Green 有 host/worker 协议版本，一旦错配就是「打开就崩」。整包一致是最便宜的解法。

### P10 不抢默认打开方式，只进「打开方式」

**来源**：ElyOffice（文件类型只进「打开方式」，从不设为默认）。
**结论**：安装包注册能力，不劫持关联。
**判断**：这是降低「装个软件把我 Word 改了」这类抵触的最低成本手段，也避免与 Office/WPS 的关联争夺战。

### P11 未验证的能力不写成已完成

**来源**：ElyOffice 规则第 10 条与其兼容性清单的写法（逐项写「已验证/受限/未验证」）。
**结论**：Green 的格式能力矩阵必须逐项标注验证状态与验证环境。
**判断**：文档编辑器的用户预期是「和 Word 一样」。任何未被实测覆盖的能力，一旦被写进宣传，就会变成缺陷单。

### 4.7 生态结论

1. **文本侧足够成熟**，Markdown/纯文本编辑器可以全 Rust 做到生产级。
2. **OOXML 侧是「模型可用、排版空白」**。不要幻想用 `docx-rs` 做出 Word 级所见即所得。
3. **PPTX 是硬缺口**，必须 LOK。
4. **PDF 有干净的 BSD 选择（PDFium）**，代价是编辑深度有限。
5. **UI 框架没有「既成熟又适合文档编辑器」的选项**：GPUI 性能与形态最合适但需 fork；Tauri 成熟但违背「Rust 为主」；Slint 许可不可接受。这是 D-tech 决策的核心张力。

## 5. 架构决策：A / B / 混合

### 5.1 方案 A（WPS 式分离聚合）

各格式是独立应用/模块，外面套启动器或工作台聚合。

- 成立的理由：进程/模块隔离天然；每个格式可以独立发版；LOK 的多文档能力可以按应用切开；符合 ElyOffice 的既有实践。
- 代价：
  - 用户心智回到「先选应用」。需求 3（内容优先、不把注意力移开）直接冲突。
  - 跨格式操作（把表格粘进文档、把文档导出成 PDF、在 PDF 里引用 docx 的一页）需要额外的进程间编排。
  - 插件要装 N 次、授权 N 次，市场体验割裂。
  - 启动器本身会变成第二个「应用」，与「一个窗口」冲突。

### 5.2 方案 B（万能统一外壳）

只开一个文档窗口，按内容自动选择渲染/编辑能力。

- 成立的理由：体验最纯粹；插件只需面向一个宿主；跨格式共享一套命令与快捷键。
- 代价：
  - **单进程承载所有引擎 = 单点故障**。LOK 崩溃、pdfium 死锁、一个 2 GB 的 xlsx 都会带走整个应用。
  - **交互模型不可统一**。文档是流式排版，表格是二维网格 + 公式求值，幻灯片是画布 + 时间轴，PDF 是固定页面。把它们塞进同一个「内容」抽象，最后会得到一个谁都不好用的抽象。
  - **「按内容自动选」是危险的**：`.docx` 被识别成 Markdown 文本视图、`.xlsx` 被当成 CSV 只读，用户会认为文件被损坏。格式判定必须保守、可见、可覆盖。
  - 引擎线程模型冲突：LOK 要求固定线程与自建事件循环；pdfium 要求串行；自绘文本要求 UI 线程。合并进一个进程后，调度会变成互相等待。

### 5.3 推荐：方案 C（单壳多引擎）

**一句话**：外壳是单应用单窗口（B 的体验），引擎是多进程多模块（A 的边界）。

```
┌─────────────────────────────────────────────────────────────┐
│ Green.exe（UI 进程）                                         │
│  shell: 标题/工具条/状态栏/命令面板/设置                       │
│  doc:   文档会话、脏状态、撤销、自动保存、崩溃恢复              │
│  surface: 文本表面 | 网格表面 | 页面表面 | 画布表面             │
│  plugin: 清单、权限、WASM 运行时、市场客户端                    │
└───────┬──────────────────┬──────────────────┬───────────────┘
        │ 命名管道 + 共享内存 │                  │
┌───────▼────────┐ ┌───────▼────────┐ ┌───────▼────────┐
│ office-worker  │ │ pdf-worker     │ │ plugin-worker  │
│ LibreOfficeKit │ │ PDFium         │ │ wasmtime       │
│ docx/xlsx/pptx │ │ 渲染/批注/表单  │ │ 第三方格式插件  │
└────────────────┘ └────────────────┘ └────────────────┘
        │
┌───────▼────────┐
│ convert-worker │  导入/导出/另存（可超时、可杀）
└────────────────┘
```

**为什么这样切**

1. **用户侧只有一个应用**：满足需求 3，且插件只面向一个宿主。
2. **引擎侧按格式分进程**：满足 C3；一个格式的引擎崩溃不影响其他文档，也不影响外壳。
3. **表面（surface）是唯一的渲染契约**：外壳不知道也不关心内容来自 LOK 位图还是自绘字形。这正是「更好的 Excel」插件能替换网格表面的前提。
4. **不做格式自动切换的猜测**：判定顺序为扩展名 → 魔数 → OOXML 内容类型 → 用户指定；判定结果在状态栏可见，可手动「用其他方式打开」。这是对纯 B 的关键修正。

**代价（必须承认）**

- 比纯 A 多一层 IPC 与表面抽象，早期开发量更大（估计多 15–20%）。
- 位图跨进程传输需要共享内存 + 脏矩形，否则会掉帧。
- 调试链路更长：一个问题可能横跨 UI、IPC、worker、上游引擎。
- 单窗口意味着「同时看两份文档」要靠新窗口（同一进程），不能靠 tab；这是产品取舍。

### 5.4 用户可见行为

| 场景 | 行为 |
| --- | --- |
| 双击 `.md` | 同一个 Green 窗口，正文区渲染 Markdown，工具条出现文本格式组 |
| 双击 `.xlsx` | 同一窗口，正文区变网格，工具条出现表格组；工作表标签在正文底部（属于内容，不是 chrome） |
| 双击 `.pptx` | 同一窗口，正文区变幻灯片画布；缩略图条按需浮出（`Ctrl+Shift+1`） |
| 双击 `.pdf` | 同一窗口，连续页面滚动；工具条出现批注/页面组 |
| 打开第二个文件 | 默认在同一进程新开窗口（不是 tab）；可用设置改为「替换当前文档」 |
| 引擎崩溃 | 正文区显示「引擎已重启，正在恢复」；从日志恢复到最后一个已提交编辑 |

> 备注：不提供 tab 是刻意的。WPS 的「整合模式」用 tab 解决多文档切换，但 tab 会把注意力引到「管理文档」而不是「写内容」。Green 用「新窗口 + 命令面板快速切换」替代。

## 6. 总体架构与模块边界

### 6.1 进程视图

| 进程 | 职责 | 生命周期 | 失败影响 |
| --- | --- | --- | --- |
| `green.exe` | 外壳、文档会话、表面合成、插件宿主 | 用户会话 | 全崩（尽力避免） |
| `green-office-worker.exe` | 承载 LibreOfficeKit；docx/odt/xlsx/ods/pptx/odp | 按需启动，可常驻一个空闲实例 | 该文档引擎重启 |
| `green-pdf-worker.exe` | 承载 PDFium；渲染、文本层、批注、表单 | 按需启动 | 该文档重开 |
| `green-convert-worker.exe` | 导入导出、批量转换、格式探测兜底 | 一次性 | 转换任务失败 |
| `green-plugin-worker.exe` | 运行 WASM 插件实例 | 按需 | 插件实例终止 |

**规则**：worker 不创建窗口、不弹系统对话框、不访问用户文档目录（除宿主显式授权的临时目录）。worker 只认一个端点、一个令牌。

### 6.2 crate 边界

| crate | 职责 | 不允许依赖 |
| --- | --- | --- |
| `green-app` | 组合根：窗口、启动流程、单实例转发 | 具体引擎 crate |
| `green-shell` | 标题栏、工具条、状态栏、命令面板、快捷键 | 文档模型细节 |
| `green-doc` | `DocumentHost` 契约、会话状态机、脏状态、撤销协调、自动保存、崩溃恢复 | 任何引擎实现 |
| `green-surface` | `Surface` 契约、输入事件路由、命中测试的公共类型 | 具体表面实现 |
| `green-text` | 文本缓冲、块索引、Markdown 解析、编辑操作、选区 | UI |
| `green-layout` | parley 封装、块排版缓存、增量重排与收敛、行索引 | 引擎 |
| `green-native-md` | Markdown 表面（内置插件，走插件接口） | 引擎 |
| `green-ipc` | 帧协议、握手、取消、共享内存、背压 | 业务类型 |
| `green-engine-office` | LOK 宿主与命令白名单（worker 侧） | UI |
| `green-engine-pdf` | PDFium 宿主（worker 侧） | UI |
| `green-plugin` | 清单解析、版本求解、权限判定、WASM 宿主、市场客户端 | 具体插件 |
| `green-platform` | Win32：命名管道、共享内存、DPI、单实例、任务栏、剪贴板、IME | 业务 |
| `green-ui-kit` | 按钮/表单/浮层等基础组件 | 文档模型 |

**不变量（代码评审要守的）**

1. UI 线程不得阻塞在 IPC 上；所有 worker 调用都是异步 + 可取消。
2. UI 线程不得持有 worker 的锁；跨进程只有消息。
3. 引擎 crate 不得依赖 `green-shell` / `green-ui-kit`。
4. 任何写入磁盘的路径必须经过 `green-doc` 的保存管线（原子写 + 日志）。
5. `green-ipc` 的类型只允许用 `postcard`/CBOR 可描述的 POD；不允许传 trait 对象或指针。

### 6.3 线程模型（UI 进程）

| 线程 | 职责 | 禁止 |
| --- | --- | --- |
| main / UI | 事件循环、绘制、输入 | 磁盘 IO、排版、等待 worker |
| layout | 块排版、增量重排、行索引构建 | 碰 UI 句柄 |
| io | 读文件、自动保存、日志追加 | 碰 UI |
| font | 启动时枚举字体、构建/加载字体索引缓存 | 排版 |
| ipc | 管道读写、共享内存映射、帧解码 | 业务逻辑 |

> 实测依据：字体枚举单项 180 ms，必须放在启动早期并行做，并缓存索引；排版单线程 108 ms/348 块，放后台线程即可，不需要线程池（见 §9.4）。

### 6.4 IPC 协议

- 传输：Windows 命名管道 `\\.\pipe\green-{sid}-{session}`；仅本用户可连（管道的 security descriptor 限定当前 SID）。
- 帧：`u32` 长度前缀 + `postcard` 序列化的枚举。协议版本 `PROTOCOL: u16`，握手交换 `protocol`、`engine_build`、`capabilities`。
- 位图：`CreateFileMapping` 共享内存，BGRA8；帧消息带 `seq`、`dirty: Vec<Rect>`、`scale_factor`。
- 背压：宿主给 worker 发信用额度（最多 N 个未确认帧）；worker 未获额度不产生新帧。
- 取消：每个请求带 `request_id`；`Cancel(request_id)` 不保证停止底层计算，但保证结果被丢弃。
- 超时：打开 10 s、命令 2 s、保存 30 s（可配置）；超时后宿主标记引擎「无响应」，不杀进程（避免丢未保存内容），但提示用户。

消息集合（v1）：

```text
Host -> Worker: Hello, Open{path|bytes, format, viewport, scale}, Close,
                SetViewport, Input{event}, Command{id, args}, Save{target},
                Export{format, target}, Cancel{request_id}, Shutdown
Worker -> Host: HelloAck{protocol, engine_build, caps}, Opened{info, caps},
                Frame{seq, dirty, shm}, Cursor{rect, shape}, Selection{rects},
                CommandDone{request_id, result}, SaveDone{path, bytes},
                Error{code, message, detail}, Progress{phase, pct}
```

### 6.5 文档会话状态机

```text
Idle
 └─ Open(path) ──> Detecting ──> Opening(worker) ──> Ready{ReadOnly|Editable}
                                        │                    │
                                        │                    ├─ Edit ──> Dirty
                                        │                    ├─ Save ──> Saving ──> Ready
                                        │                    └─ Close ─> Closing
                                        └─ fail ──> Failed{reason, recovery?}

Ready/Dirty ── worker death ──> EngineLost ──> Recovering(journal) ──> Ready(新引擎)
```

- **自动保存**：编辑后 800 ms 或每 200 次操作（先到者），写 `%LOCALAPPDATA%\Green\journal\{doc_id}\`；格式为「快照 + 追加操作日志」，恢复到最近一次快照 + 重放。
- **保存**：写临时文件 → fsync → 原子替换（`ReplaceFileW`）；保存前检查磁盘上的文件是否被外部修改（`notify` + mtime + 哈希），冲突时提示，不静默覆盖。
- **崩溃恢复**：`EngineLost` 后不自动重开原文件（可能再次崩），而是进入恢复视图：展示日志中的内容，允许「另存为」或「重试」。

### 6.6 `DocumentHost` 契约

```rust
pub trait DocumentHost {
    fn info(&self) -> DocInfo;              // 格式、页数/行数、只读、能力
    fn surface(&self) -> SurfaceKind;       // Text | Grid | Page | Canvas
    fn apply(&mut self, edit: Edit) -> Result<EditOutcome>;   // 唯一写入口
    fn snapshot(&self, range: BlockRange) -> Option<Snapshot>; // 导出/复制/索引
    fn save(&mut self, target: SaveTarget) -> Result<SaveReport>;
    fn command(&mut self, cmd: CommandId, args: &[Arg]) -> Result<()>;
}
```

- `apply` 与 `command` 分开：`apply` 是结构化编辑（只有文本/网格表面有），`command` 是白名单命令（所有引擎都有）。
- `EditOutcome` 带 `dirty: Vec<BlockId>`，供表面做最小重绘。
- `snapshot` 是唯一允许跨格式读取内容的入口（导出、搜索索引、复制到剪贴板）。

## 7. 插件 API 与插件市场

### 7.1 插件种类

| 类型 | `kind` | 例子 | 能力 |
| --- | --- | --- | --- |
| 格式 | `format` | Markdown、Git tree、CSV、JSON Lines | 声明扩展名/魔数，提供「文档树」；可选提供表面 |
| 视图 | `view` | Git 历史视图、大纲、文档地图 | 向命令面板/浮层贡献视图，不接管正文 |
| 增强 | `enhance` | 更好的 Excel、公式编辑器、批量重命名 | 贡献命令、上下文菜单、可选替换某个 capability |
| 转换 | `convert` | DOCX→Markdown、PDF→图片 | 注册导入/导出来源与目标 |

**「更好的 Excel 支持」如何落地**：它不是「另一个 xlsx 解析器」，而是注册 `capability = office.grid` 的高优先级 provider：
- 默认 provider：LOK Calc 画布 + 外壳网格覆盖层（公式栏、名称框、填充柄）。
- 增强 provider：可以只替换「覆盖层行为」（低风险，声明式），或整体替换网格表面（高风险，需 `surface.replace` 权限 + 可信签名）。

这样同一个插件机制既覆盖「加个格式」也覆盖「增强内置能力」，不需要两套 API。

### 7.2 清单

```json
{
  "id": "com.example.better-excel",
  "name": "更好的 Excel 支持",
  "version": "1.4.0",
  "api": 1,
  "kind": "enhance",
  "requires": {
    "green": ">=0.4,<1",
    "plugins": [{ "id": "com.green.core-sheets", "range": "^1" }]
  },
  "contributes": {
    "capabilities": [{ "name": "office.grid", "priority": 50, "mode": "overlay" }],
    "commands": [{ "id": "pivot.create", "title": "创建数据透视表", "when": "surface == grid" }],
    "fileTypes": []
  },
  "permissions": ["document.read", "document.write", "clipboard.read"],
  "entry": "plugin.wasm",
  "min_host_memory_mb": 256
}
```

- `api` 是宿主插件 API 的主版本；宿主对 `api: 1` 承诺兼容到 1.x 结束。
- `contributes.fileTypes` 里每项含 `ext`、`magic`（十六进制前缀，可选）、`mime`、`sniff`（WASM 里的小函数，限制 5 ms）。
- 清单本身签名（包签名覆盖清单与所有文件哈希）。

### 7.3 版本与依赖

- **语义化版本**：`major.minor.patch`；预发布用 `-beta.N`。
- **宿主 API 版本**：单调整数 `api`。破坏性变更 → `api += 1`；旧 `api` 的插件在至少 2 个 minor 版本内继续可用（适配层），之后进入「仅可卸载」状态。
- **依赖解析**：插件→插件依赖使用 semver range；解析策略是「每个 id 只允许一个版本」（不做 side-by-side），冲突时给出具体冲突链并要求用户选择或让插件作者放宽范围。理由：文档编辑器的插件会改同一份文档，多版本共存会让「哪个插件改了它」不可追踪。
- **依赖不是能力**：A 依赖 B，不代表 A 获得 B 的权限；A 必须在自己的清单里声明所需权限。
- **循环依赖**在安装时拒绝。
- **更新**：patch 自动提示，minor/major 需用户确认；权限集扩大时强制重新确认（展示 diff）。保留上一版本用于回滚。

### 7.4 权限

| 权限 | 含义 | 默认 | 授予方式 |
| --- | --- | --- | --- |
| `document.read` | 读取当前文档的文本/结构 | 询问 | 安装时一次性 |
| `document.write` | 通过 `Edit` 修改当前文档 | 询问 | 安装时一次性 |
| `document.metadata` | 标题、作者、路径、页数 | 允许 | 隐式 |
| `clipboard.read` / `clipboard.write` | 剪贴板 | 询问 | 安装时 |
| `fs.read` | 读文件；范围 `document-dir` / `any` | `document-dir` 允许 | `any` 需显式开启并二次确认 |
| `fs.write` | 写文件；同上 | 拒绝 | 显式开启 |
| `net` | 网络；必须列域名 | 拒绝 | 显式开启，逐域 |
| `shell.command` | 贡献工具条/菜单/命令面板项 | 允许 | 隐式（低风险） |
| `surface.overlay` | 在正文上绘制浮层（批注、提示） | 询问 | 安装时 |
| `surface.replace` | 接管正文表面 | **拒绝** | 仅「可信」插件，且需签名验证 + 用户二次确认 |
| `process.spawn` | 启动外部进程 | **拒绝** | 内置白名单之外一律不授予 |

- **最小权限**：WASM 默认没有环境能力，所有 host function 逐调用检查权限；权限检查在宿主侧，不在插件侧。
- **信任等级**：`builtin`（随包）> `verified`（市场实名发布者 + 人工审核）> `community`（自动扫描）。`surface.replace` 与 `process.spawn` 只对 `builtin`/`verified` 开放。
- **配额**：单次调用燃料上限（如 2000 万条指令）、内存上限（默认 64 MB，可声明到 256 MB 需审核）、单次事件墙钟 100 ms。超限 → 终止实例 + 禁用插件 + 提示。
- **审计**：每个插件的能力调用记一条结构化日志（不含正文），可在「插件 → 活动」里查看。

### 7.5 运行时与沙箱

- **默认：WASM（wasmtime）**。理由：默认无环境能力、可计量、可终止、跨平台、能复用同一套宿主函数做权限检查。
- **渲染模型：声明式优先**。插件返回「块树 + 属性」，宿主用内置渲染器绘制。这样插件无法伪造 chrome、无法越权绘制到工具条，也不会因自绘导致高 DPI/无障碍缺失。
- **例外：可信表面插件**可以获得「绘制命令列表」接口（矩形、路径、文本 run、图片），由宿主执行；仍然不能直接碰 GPU。
- **原生插件（dylib/进程）不进 v1**。理由：Windows 上没有便宜的沙箱，原生插件会让「权限」变成装饰。若将来必须（例如某格式只有 C 库），走「插件自带 worker 进程 + 能力声明」的独立通道，单独评审。

### 7.6 市场

- **索引**：`index.json`（可镜像），字段含 id、名称、图标、分类、各版本、哈希、最低宿主版本、权限摘要、信任等级、下载地址。索引整体 ed25519 签名；客户端内置公钥，签名不符即拒。
- **包**：`.greenpkg` = zip（清单 + wasm + 资源 + `signature`）。安装时校验：签名 → 哈希 → 权限清单 → 与已装插件的依赖冲突。
- **离线安装**：支持本地 `.greenpkg`，权限提示一致。
- **列表与搜索**：本地缓存索引，支持按「格式/视图/增强」筛选；不做评分系统（v1 没有可信数据源，做评分只会变成刷分场）。
- **下架与撤回**：索引可标记 `revoked`；客户端在下次检查时禁用并提示，不静默卸载。
- **国内网络**：索引与包支持自定义镜像地址；不做强制在线校验。

### 7.7 内置即插件

Markdown、Git tree、CSV 以内置插件形式实现，走与第三方相同的清单、权限、贡献点，只是信任等级为 `builtin` 且随包分发。

- 好处：插件 API 从第一天就被真实需求压测；不会出现「内置能做的插件做不了」。
- 代价：早期接口演进会拖慢内置功能开发；需要「内置实现可以直接调宿主内部 API」的逃生舱（仅 `builtin` 可用，且在接口稳定后逐步移除）。

## 8. 各格式的接入方式

### 8.1 能力矩阵（v1 目标，必须逐项实测后更新）

| 格式 | 引擎 | 查看 | 基础编辑 | 高保真编辑 | v1 明确不支持 |
| --- | --- | --- | --- | --- | --- |
| DOCX | LOK (Writer) | ✅ | ✅ 文字、段落、样式 | ✅（受 LOK 与字体约束） | 宏、域代码深度编辑、部分 SmartArt |
| ODT | LOK | ✅ | ✅ | ✅ | 同 DOCX |
| XLSX | LOK (Calc) + 外壳覆盖层 | ✅ | ✅ 单元格、公式、格式 | ⚠️ 图表/透视/条件格式部分 | Power Query、外部数据连接 |
| PPTX | LOK (Impress) | ✅ | ✅ 文本、形状、版式 | ⚠️ 动画/切换子集 | 媒体播放依赖系统解码器 |
| PDF | PDFium | ✅ | ✅ 批注、表单、页面增删排序 | ❌ 正文重排编辑 | 文本重排、OCR（v1 不做） |
| Markdown | 自研（parley） | ✅ | ✅ | ✅（源码为权威） | 协同、插件化语法扩展（v1 只读扩展） |
| Git tree | 自研 + Git CLI | ✅ | 只读 + 检出 | — | 合并冲突图形化（v1 只做文本） |

> 「⚠️」表示依赖 LOK 的实际能力与我们的覆盖层，必须在 M0/M3/M4 用真实文件验证后再定级。

### 8.2 DOCX：LOK 位图 + 命令白名单

**接入方式**

1. `office-worker` 启动 LOK，`lok_init` 一次；打开文档得到 `LokDocument`。
2. 视图：`postRender` 回调拿到整页/图块位图（BGRA），写入共享内存，发 `Frame`；宿主按 `dirty` 区域更新纹理。
3. 输入：鼠标/键盘/IME 组合事件经 IPC 转成 LOK 事件（`postMouseEvent`/`postKeyEvent`）；坐标要除以缩放并加上滚动偏移。
4. 编辑：工具条按钮 → `CommandId` → worker 侧映射为 UNO 命令字符串（白名单），`lok_dispatch_command`。
5. 选区与对象手柄：LOK 只给矩形与光标信息；对象选中框、旋转手柄、拖动由外壳自绘（ElyOffice 的 `handles.rs`/`carry.rs` 就是干这个）。
6. 保存：`lok_save_as` 到临时文件，宿主原子替换；保存前记录 LOK 的「文档修改」标志，避免无改动也写盘。

**必须自建的部分（不要低估）**

- 图块（tile）画布：只渲染视口内的图块，滚动时复用；否则 200 页文档会一次性产生巨大位图。
- 输入桥：坐标变换、滚动、双指缩放、IME 候选窗定位。
- 无障碍：LOK 只报当前段落；需要补丁 + 自建 UIA 树。
- 自建对话框：LOK 自己的对话框要立即关闭并报错，由外壳重建（字体缺失、打印、链接更新等）。
- 字体：文档用的字体若系统没有，LOK 会替换，导致跑版。必须在打开时检测缺失字体并提示。

**风险**：这是整个项目最大的工作量与最强的上游耦合。ElyOffice 的 149 个补丁就是这条路的价格标签。

### 8.3 XLSX：LOK Calc + 外壳覆盖层

- 网格本身由 LOK 渲染（保证与 Excel 一致的版式与公式结果）。
- 外壳负责 **公式栏、名称框、填充柄、选区统计、工作表标签栏**。这些不是 chrome，是表格内容的一部分（对应已有缺口：ElyOffice 的「表格公式栏与名称框」是自建的）。
- 冻结窗格、筛选、排序优先走 LOK 命令；LOK 不支持的（如大型数据清洗）由增强插件以「导出选区 → 处理 → 回写」的方式做。
- 10 万行级文件的打开时间必须实测；LOK 在超大表上的表现是 M4 的门槛指标。

### 8.4 PPTX：LOK Impress + 幻灯片条

- 画布与文档一致（位图 + 输入桥）。
- 幻灯片缩略图条是**按需浮层**（`Ctrl+Shift+1` 或鼠标移到左边缘），不常驻，符合 P2。
- 放映模式：全屏窗口 + 键盘/翻页器；媒体播放交给系统解码器（Windows Media Foundation），失败时明确报错。
- 章节、备注页、母版视图：v1 只做备注页查看；母版编辑推迟。

### 8.5 PDF：PDFium，只读为主 + 标注编辑

**为什么不选 MuPDF**：MuPDF 是 AGPL-3.0，会把发行包整体拖进 AGPL（ElyOffice 的 ElyPDF 就是这样）。Green 若要保持自有代码许可自由，必须避开。PDFium 是 BSD-3-Clause，`pdfium-render` 是 MIT/Apache-2.0。

**能力边界**

- 做：渲染（分页虚拟化）、文本层抽取与选择复制、搜索、缩放/旋转、页面增删排序裁剪、批注（高亮/下划线/删除线/便签/图章）、表单字段填写、文档属性、附件、打印。
- 不做：正文重排编辑（把 PDF 当 Word 改）、OCR、数字签名（v1 只做签名存在性检查）。
- 理由：PDF 是「固定版式」格式，重排编辑本质上要重建文档模型，等于再做一个 Word；而用户对 PDF 编辑的真实需求 80% 是标注、填表、改页序。

**实现要点**

- PDFium 非线程安全：所有调用在 worker 的单一专用线程上串行；宿主侧不并发发请求。
- 页面虚拟化：维护 `page -> 高度/位图` 的 LRU；预取前后各 2 页；缩放变化时按新 DPI 重渲染可见页，旧位图保留到新帧到达（避免闪烁）。
- 文本选择：用 `FPDFText_*` 取字符框，自建选区与复制；跨页选择要处理页间偏移。

### 8.6 Markdown 与 Git tree

**Markdown**

- 权威：磁盘上的原文（满足 P1）。内存：`Rope` + 「块索引」（每块的字节范围、类型、行范围）。
- 解析：`pulldown-cmark` 全量解析（实测 0.11 ms/5 万字），产出块列表；不做增量解析器的复杂度投入，只做**增量排版**。
- 排版：`parley`，每块一个 layout；块内按行缓存；编辑时从改动行向下重排直到收敛（§9.4）。
- 渲染：逐段「所见即所得」——光标不在的块渲染为富文本（标题字号、粗斜体、列表符号、代码块底色、表格），光标进入的块显示必要语法符号（淡化）。这与 Typora 的「what you see is what you mean」一致。
- 不支持就明确不支持：内嵌 HTML 只做安全白名单渲染；脚注/定义列表按 GFM 子集。
- 大文件：超过 5 MB 或 100 万字符进入「大文件模式」——纯源码视图 + 语法高亮，顶部提示可切回富文本。

**Git tree**

- 只读视图 + 基础操作（检出、暂存、提交）。Git 通过 CLI 子进程调用（参数数组，不经 shell），与 ElyOffice 一致；不链接 libgit2，避免 GPL/构建负担。
- 非 Git 仓库的目录：降级为文件树（同一种 surface）。

### 8.7 导入导出

- 统一走 `convert-worker`：`Import(path) -> Document`、`Export(doc, format) -> path`。
- 转换表：Markdown → DOCX/PDF/HTML；DOCX → PDF/Markdown（保真度标注为「结构保留，样式近似」）；XLSX → CSV；PPTX → PDF/PNG。
- 导出任务可取消、可超时；失败不产生半成品文件（先写临时文件）。
- **不做「另存为任意格式都完全保真」的承诺**；导出对话框必须显示「将丢失什么」。

## 9. 超长文档的性能方案

### 9.1 指标定义（可测）

所有指标都在固定机型（见 §9.6）上、对固定 fixture、跑 20 次取分位。

| 指标 | 定义 | 目标（5 万字 Markdown） | 测量方法 |
| --- | --- | --- | --- |
| **T_cold_start** | 进程创建 → 主窗口可交互（能响应命令面板） | ≤ 800 ms p95 | 进程启动打点 + ETW |
| **T_first_paint** | 进程创建 → 首帧包含文档正文前 3 行 | ≤ 300 ms p95 | 首帧回调时间戳 |
| **T_first_input** | 进程创建 → 光标可见且接受首个按键 | ≤ 400 ms p95 | 注入按键，记录 `WM_KEYDOWN` 到下一帧呈现 |
| **K2P（按键到像素）** | 平台 `WM_KEYDOWN` 入队时间 → 含新光标的帧呈现时间 | p50 ≤ 8 ms，p95 ≤ 16 ms，p99 ≤ 33 ms；>16 ms 的按键占比 < 1% | 见 §9.6 的帧标记法 |
| **Reflow_block** | 单次编辑引发的块内重排耗时 | p95 ≤ 4 ms | 内部计时器 |
| **Frame_time（滚动）** | 连续滚动 3 秒内每帧 GPU 提交间隔 | p95 ≤ 16.7 ms（60 Hz）；掉帧率 < 1% | DXGI 帧统计 |
| **T_full_layout** | 后台完成全文排版的耗时（不阻塞输入） | ≤ 1.5 s | 后台任务计时 |
| **Mem_open** | 打开后的进程工作集 | ≤ 300 MB | `K32GetProcessMemoryInfo` |
| **Mem_growth** | 连续 1 万次编辑后的工作集增长 | ≤ 5% | 同上 |
| **输入到撤销可用** | `Ctrl+Z` 到界面回滚完成 | ≤ 50 ms p95 | 注入按键 |

> 「不卡顿」在本项目里的可执行含义：**K2P p95 ≤ 16 ms 且掉帧率 < 1%，且没有任何单次操作让 UI 线程阻塞超过 50 ms**。第三项用「UI 线程长任务检测」单独度量（超过 50 ms 记一次 violation，发布门槛为 0）。

### 9.2 实测基线（本机）

fixture：50,130 字符 / 123 KB / 348 块 / 1243 行（宽 800 px、16 px 字号、28 px 行高）。

| 环节 | 中位 | 最大 | 备注 |
| --- | --- | --- | --- |
| pulldown-cmark 全量解析 | 0.11 ms | 0.37 ms | 3162 个事件 |
| comrak 全量解析 | 0.31 ms | 0.60 ms | 建 AST |
| ropey 插入/删除 | p50 0.0002 ms | p99 0.0025 ms | 4000 次操作 |
| cosmic-text 整篇一个 buffer | 185–197 ms | — | 1592 个 layout run |
| cosmic-text 按块排版 | 104–108 ms 合计 | 1.5–2.6 ms/块 | 中位 0.35 ms/块 |
| 最慢块重排 | 0.35 ms | 0.36–0.39 ms（p95） | 204 字符 |
| 首屏（12 块填满 1200 px） | 3.45–3.53 ms | — | — |
| `FontSystem::new()` | 180–195 ms | — | 字体枚举，必须缓存 |
| 16 线程 × 16 个 FontSystem 并行 348 块 | 823–946 ms | — | 比单线程慢 7.6–9 倍 |
| 进程工作集（单 FontSystem） | 43 MB | — | 16 个 FontSystem 时 105 MB |

**读法**

1. 解析与文本缓冲比预算小三个数量级——**不要在这两处做优化，也不要为它们引入复杂度**。
2. 排版是唯一需要设计的部分；整篇一个 buffer 是错的，按块是必须的。
3. 字体枚举 180–195 ms 比首屏排版（3.5 ms）大 50 倍以上；冷启动优化应优先打这里。
4. 并行排版在没有共享字形缓存前是负优化。这条要写进代码注释，否则一定会有人「顺手并行一下」。

### 9.3 预算推导（T_first_paint ≤ 300 ms）

| 阶段 | 预算 | 依据 |
| --- | --- | --- |
| 进程创建 + 加载 DLL（含 worker 按需） | 120 ms | 经验值，需实测；worker 不在首屏路径上 |
| 字体索引（缓存命中） | 15 ms | 冷枚举 180–195 ms，缓存后应为个位数到十几 ms；**必须做** |
| 读取 + 解析 5 万字 | 5 ms | 实测 0.11 ms 解析 + IO |
| 首屏排版（12 块） | 10 ms | 实测 3.5 ms，留 3× 余量 |
| 首帧提交 + 呈现 | 30 ms | 含 DWM 合成 |
| 余量（杀软/冷缓存/机械盘） | 120 ms | 现实世界折扣 |

> 结论：**首屏预算里没有「排版」的位置问题，只有「启动与字体」的位置问题**。如果实测超标，先查字体索引与 DLL 加载，不要先改排版。

### 9.4 方案

**A. 块索引 + 行索引**

- 块：段落、标题、列表项、代码块、表格、引用、分隔线、图片。块有稳定 `BlockId`（不是下标，编辑后不失效）。
- 行：每块维护 `Vec<LineBreak { byte_range, y, height }>`；行是重排的最小单位。
- 索引更新：编辑落在某块 → 只标脏该块；结构变化（插入/删除块）→ 标脏该块及其后继直到「块高度不再变化」。

**B. 增量重排 + 收敛**

```
on_edit(block, changed_range):
    reflow from the line containing changed_range.start
    for each subsequent line:
        compute new break & y
        if new break == old break && new y == old y: stop   # 收敛
    mark dirty union of visited lines
```

- 单段 5 万字（最坏情况）：只有一段时块级失效无意义，全靠行级收敛。实测单块重排 0.34 ms/204 字符，5 万字单段约 80–200 ms（线性外推，需实测验证）——**因此必须收敛，不能每次整段重排**。若收敛失败（例如在段首插入导致后续全部错位），采用「分帧重排」：每帧最多重排 200 行，光标先行，视觉上允许短暂的行位置变化。
- 表格：单元格内按文本规则；列宽变化才重排整表。

**C. 输入路径**

1. `WM_KEYDOWN` → 入队（记录时间戳 `t0`）。
2. 编辑操作应用到 `Rope`（微秒级）。
3. 标脏 → 同步重排「当前行 + 收敛范围」（预算 4 ms）。
4. 提交绘制 → 记录帧呈现时间 `t1`；`K2P = t1 - t0`。
5. 若重排超预算：先绘制「光标 + 未重排的旧行」，把重排推到下一帧（视觉上允许一行内的字临时错位，不允许光标丢失）。

**D. IME**

- 组合期间（`WM_IME_COMPOSITION` 未提交）：把 preedit 作为**浮层**绘制在光标处，不进入文档模型、不触发重排。
- 提交时一次性插入，走正常编辑路径。
- 候选窗定位用光标矩形 + DPI 换算；不要在组合期间移动正文。

**E. 虚拟化**

- 只绘制视口 ± 1 屏的块；视口外的块保留高度（来自行索引），不保留字形。
- 滚动时按需排版进入视口的块（预算：每帧最多 8 块）。
- 缩略图/大纲用「采样排版」（只算行数与高度，不算字形）或后台低优先级排版。

**F. 字体**

- 启动时枚举一次，写入 `%LOCALAPPDATA%\Green\cache\fonts-v{N}.bin`（含 family、style、覆盖码点范围、路径、mtime）；下次启动直接 mmap。
- 字体变化（安装/卸载）用 mtime 与目录快照校验，失效则重建。
- 缺字体：文档声明但系统没有的字体，列出并用度量兼容的替代（如 SimSun → 思源宋体），提示用户；**不要静默替换**。

**G. 内存**

- 字形缓存按块 LRU（默认上限 64 MB）；位图缓存按页 LRU（PDF 默认 128 MB）。
- 撤销历史按「操作 + 反向操作」存，不存全文快照；超过 2000 步或 50 MB 时折叠最旧的部分。

### 9.5 对抗性用例（必须进 CI）

| 用例 | 为什么危险 | 门槛 |
| --- | --- | --- |
| `md-50k-single-paragraph.md` | 块级失效完全失效，只能靠行级收敛 | K2P p95 ≤ 16 ms |
| `md-50k-no-newline.md`（一行 5 万字） | 断行算法 O(n²) 退化风险 | 首屏 ≤ 300 ms，滚动 p95 ≤ 16.7 ms |
| `md-5mb.md` | 触发大文件模式 | 不崩溃，进入只读源码模式 ≤ 1 s |
| `md-50k-cjk-latin-mixed.md` | 字体回退 + bidi | K2P p95 ≤ 16 ms，无错位 |
| `md-50k-with-1000-images.md` | 图片解码与内存 | Mem ≤ 500 MB，滚动不卡 |
| `xlsx-100k-rows.xlsx` | LOK Calc 大表 | 打开 ≤ 5 s，滚动 p95 ≤ 33 ms |
| `pdf-1000p.pdf` | 页面虚拟化 | 首屏 ≤ 500 ms，翻页 ≤ 100 ms |
| `docx-200p.docx` | LOK 排版与图块 | 打开 ≤ 2 s（对齐 Word 的 1.1 s 量级） |

### 9.6 验证方式

1. **基准 harness**：`research/bench` 扩展到「可注入的 fixture + 固定迭代 + JSON 输出」，纳入 CI。
2. **K2P 埋点**：在窗口过程记录 `WM_KEYDOWN` 的 `GetMessageTime`，在呈现线程用 `DXGI_PRESENT` 后的 `QueryPerformanceCounter` 记录；两者相减。为避免测量本身影响性能，采样率 100%（成本是两个计时调用）。
3. **UI 线程长任务**：在消息循环里插入「任务开始/结束」标记，超过 50 ms 记 violation 并写入日志（含调用栈采样）。
4. **固定机型**：一台最低配 Windows 机器（4 核 / 8 GB / 集显 / SATA SSD）+ 一台开发机；发布门槛以最低配为准。CI 用自托管 runner 跑同一台机器，避免虚拟化噪声。
5. **报告**：每次发布生成 `docs/perf/{version}.md`，含 fixture 哈希、机器信息、各指标分位、与上一版对比；回归超过 10% 阻断发布（与 ElyOffice 的「基准记录不过即不建」同思路）。
6. **不测就不写**：任何未进 harness 的格式，其「性能达标」不成立。

## 10. Windows 打包与分发

### 10.1 安装包形态

**推荐：Inno Setup 的 per-user 安装包（`GreenSetup-x.y.z.exe`）**，同时产出 MSI 供企业后续使用。

理由：

- per-user 安装不需要管理员权限，装到 `%LOCALAPPDATA%\Programs\Green`，不触发 UAC。
- LOK worker 需要多进程、命名管道、共享内存；MSIX 的容器与虚拟化虽然支持 full-trust，但会给调试与第三方引擎加载增加不确定性（ElyOffice 也选择 setup.exe，且其 Windows 包当时未签名）。
- Inno 对「按版本目录并行安装 + 文件关联 + 卸载时保留用户数据」的支持最直接。
- winget 接受 EXE 安装包（需 silent 参数与 manifest），可获得分发渠道。

**不选 MSIX 作为主渠道**：MSIX 的优势是容器隔离、差分更新、干净卸载与 Store 签名；但 LOK 的部署体量与 worker 模型更像「带运行时的原生套件」，MSIX 的收益抵不过调试成本。可作为 v2 的企业分发选项。

### 10.2 目录布局

```text
%LOCALAPPDATA%\Programs\Green\
  Green.exe
  workers\
    green-office-worker.exe
    green-pdf-worker.exe
    green-convert-worker.exe
    green-plugin-worker.exe
  engines\
    libreoffice\        # 仅 LOK 运行所需的最小集
    pdfium.dll
  plugins\              # 内置插件（随包）
    com.green.markdown\
    com.green.gittree\
  locales\
  licenses\
```

- 版本化目录：`Programs\Green\{version}\` + 一个 `current` 指针文件；更新时先装新目录再切指针，回滚只需切回。
- 用户数据（设置、日志、插件、缓存、日志）在 `%LOCALAPPDATA%\Green\`，**卸载默认保留**，仅在用户勾选时删除。

### 10.3 代码签名

事实（2026 年现状）：

- **EV 证书不再免 SmartScreen**（2024 年改版后取消 EV OID 的特殊待遇）。
- 微软推荐 **Azure Artifact Signing（原 Trusted Signing）**，约 $9.99/月；但**个人开发者仅限美国/加拿大**，组织限美/加/欧盟/英国。中国团队通常不符合资格。
- 因此现实选择是 **OV 代码签名证书**（约 $150–300/年），且私钥必须在 HSM/硬件令牌中（CA/B 论坛要求），CI 需接云 HSM（如 DigiCert KeyLocker、Sectigo Cloud Signing）。
- 未签名或自签名安装包会显示「Windows 已保护你的电脑」，部分企业策略直接阻断。

**结论**：预算 OV 证书 + 云 HSM；**每个版本用同一签名身份**（证书信誉可跨版本继承）；首个版本仍会有「无法识别的应用」提示，需在发布说明里提前告知用户（通常数周、数百次干净安装后才消失）。

### 10.4 自动更新

- 清单 `latest.json`：版本、各文件哈希、ed25519 签名、最低可升级版本、变更说明、下载地址（含国内镜像）。
- 客户端：默认「检查但询问」；下载在后台；安装需用户确认（关闭应用或重启后应用）。
- 差分：整包 zstd 压缩；先做整包，差分（bsdiff/zstd --patch-from）留到包体过大时再加。
- **不做静默安装**（与 ElyOffice 一致）：文档编辑器在用户不知情时替换自身，风险高于收益。
- **版本一致性**：host 与 worker 必须同版本；更新时整套替换。worker 握手校验 `engine_build` 与 `protocol`，不符则拒绝连接并提示修复安装。

### 10.5 文件关联与单实例

- 注册 `.docx/.xlsx/.pptx/.pdf/.md` 等为「支持打开」，**不设为默认**（P10）。安装时提供勾选项，默认不勾。
- 单实例：命名互斥体 + 命名管道转发 `Open(path)`；已在运行时，第二次启动把文件交给现有进程并退出。
- 拖放、`SendTo`、命令行 `green.exe --new-window file` 都要走同一入口。

### 10.6 崩溃与遥测

- 本地崩溃转储（minidump）写入 `%LOCALAPPDATA%\Green\crashes\`，默认**不上传**；用户可选择上传，上传前展示包含的字段（不含正文、不含路径）。
- 结构化日志：分级别、按天轮转、默认保留 7 天；日志不含文档内容。
- 更新与崩溃上报的域名可配置（企业内网可关闭）。

### 10.7 体积

- LOK 是包体大头（ElyOffice 的安装包与内核体积可作参照；具体数字需在 M0 实测）。策略：只带运行必需的最小文件集，剔除示例、帮助、非必要语言包；字体不随包（许可与体积双重原因），改用「缺字体提示 + 可选字体包」。
- 目标：安装包 ≤ 250 MB（待 M0 实测修正），安装后 ≤ 600 MB。

- WASM 运行时、权限模型、清单/依赖解析、签名索引、安装/更新/回滚 UI。
- Markdown / Git tree 改为内置插件走同一接口（验证接口足够）。
- **出口**：三个第三方示例插件（格式、视图、增强各一）在无宿主改动的情况下安装并工作；越权调用被拒绝并有日志。

### M7 增强插件与硬化（4–6 周）

- 「更好的 Excel」参考实现（覆盖层模式）；性能回归门禁；可访问性（UIA）第一版；安装包签名。
- **出口**：全部 §9.5 用例通过；UI 线程长任务 violation = 0。

> 总计约 36–47 周（单人全职不可行；按 3–4 人团队估）。M0 的结论可能改变后续排期，这是刻意的：先证伪，再投入。

## 13. 需要批准的关键决策

每条给出推荐、代价、以及「如果不批准会怎样」。

### D1 架构形态：单壳多引擎（C） vs 纯 A vs 纯 B

- **推荐**：C。外壳单应用单窗口，引擎多进程。
- **代价**：比纯 A 多一层 IPC 与表面抽象（早期 +15–20% 工作量）；比纯 B 多进程管理；调试链路更长。
- **不批准的含义**：选 A 则需求 3 无法满足；选 B 则崩溃隔离与引擎线程模型无解。

### D2 Word/Excel/PPT 引擎：LibreOfficeKit vs 纯 Rust 子集 vs 商业 SDK

- **推荐**：LibreOfficeKit（MPL-2.0），自建构建 + 补丁序列；纯 Rust（`docx-rs`/`umya-spreadsheet`）只用于大纲、抽取、轻量生成与转换兜底。
- **代价**：MPL-2.0 的文件级 copyleft（修改过的 LOK 文件必须公开补丁）；约 1 小时的内核构建；长期跟随上游；包体大（数百 MB 量级）。
- **替代**：纯 Rust 子集只能做到「打开、看、改文字」，达不到用户对 Word 的预期；商业 SDK（Aspose/Apryse 类）报价高且引入供应商锁定。
- **不批准的含义**：若拒绝 LOK，产品定位必须从「能编辑 Office 文档」降级为「能看 + 轻改」，需重新对需求 1 达成一致。

### D3 PDF 引擎：PDFium vs MuPDF

- **推荐**：PDFium（BSD-3-Clause）+ `pdfium-render`。能力范围限定为渲染/文本层/批注/表单/页序，不做正文重排编辑。
- **代价**：放弃 MuPDF 的编辑、重排、签名、OCR 能力；PDFium 非线程安全，必须单线程 worker；XFA 表单不支持。
- **不批准的含义**：选 MuPDF 会把发行包整体拖入 AGPL-3.0（ElyOffice 的 ElyPDF 即如此），自有代码的许可策略随之改变。这是一个商业决策，不只是技术决策。

### D4 插件运行时：WASM 声明式 vs JS/CEF vs 原生 dylib

- **推荐**：WASM（wasmtime）+ 声明式渲染为主，可信插件可拿绘制命令列表；v1 不做原生 dylib。
- **代价**：插件作者要写 Rust/C（或编译到 WASM 的语言），门槛高于 JS；声明式渲染限制了插件的 UI 自由度；WASM 运行时增加约数十 MB 与启动开销。
- **不批准的含义**：选 JS/CEF 则包体 +100 MB 量级、内存与启动变差、且「Rust 为主」名不副实；选原生 dylib 则权限模型形同虚设（插件可任意读写磁盘）。

### D5 Markdown 是否作为插件（内置但走同一接口）

- **推荐**：是。Markdown / Git tree 以 `builtin` 插件形式实现。
- **代价**：插件 API 必须在 M1 就设计到「够内置用」，早期接口演进会拖慢功能开发；需要保留 `builtin` 逃生舱。
- **不批准的含义**：内置功能直接调内部 API，插件接口永远没被真实压测，M6 会集中暴露设计缺陷。

### D6 安装与签名：Inno per-user + OV 证书 vs MSIX/Store vs 不签名

- **推荐**：Inno Setup per-user + OV 证书（云 HSM 签名）+ winget 清单；MSIX 留作 v2 企业渠道。
- **代价**：约 $150–300/年证书 + HSM 服务费；CI 需接云签名；首版仍有 SmartScreen 提示（数周至数月）；需自建更新器。
- **不批准的含义**：不签名 → 企业环境直接被策略阻断，且每次更新都要重新积累信誉；选 MSIX/Store → 需接受商店政策与容器限制，且 LOK 部署风险未验证。

### D7 「无侧栏无 tab」的边界：文档内部导航算不算 chrome

- **推荐**：工作表标签、幻灯片浮层、PDF 页码、大纲浮层都属于**内容**，允许存在；应用级 tab、常驻侧栏不允许。
- **代价**：需要在设计规范里逐项列举，否则实现者会各自解释；表格/幻灯片的使用习惯与「极简」有张力。
- **不批准的含义**：若连工作表标签都禁止，Excel 基本不可用；若允许常驻侧栏，则需求 3 失效。

### D8 性能门槛写进验收（300 ms / 16 ms / 1% / 0 violation）

- **推荐**：接受，并作为发布阻断条件；CI 用固定最低配机器。
- **代价**：需要一台专用机器与基准维护成本；某些功能（如超大表格）可能因达不到而延后。
- **不批准的含义**：「不卡顿」回到主观判断，需求 4 无法验收。

### D9 自有代码许可

- **推荐**：自有代码 Apache-2.0（比 MIT 多专利授权条款，对插件生态更友好）；LOK 补丁按 MPL-2.0 公开；PDFium/其他依赖按其原许可随包声明。
- **代价**：Apache-2.0 要求保留 NOTICE 与修改声明；若未来要闭源，需在贡献者协议上提前约定（建议现在就要求 CLA 或 DCO）。
- **不批准的含义**：若选闭源，仍必须公开 LOK 补丁（MPL），且无法使用 GPL 系组件；若选 MIT，专利风险略高但更简单。

### D10 v1 是否做 PDF 正文编辑

- **推荐**：不做。只做批注、表单、页序。
- **代价**：会流失一部分「用 Green 改 PDF 文字」的用户；营销上要明确边界。
- **不批准的含义**：做正文编辑等于自建 PDF 文档模型 + 重排，工作量与 Word 引擎同级，且 PDFium 不提供该能力（需 MuPDF 或自研），与 D3 冲突。

## 14. 未决与待验证

明确标出，避免被当成已结论：

1. **GPUI 能否承载富文本表面**：ElyOffice 的缺口写明「gpui 文本里不能嵌图片」，行内公式要另做。Green 的 Markdown 表面若用 GPUI 文本 API，行内图片/公式会成为限制。→ M0 验证：用 GPUI 画一个含行内图片与公式的段落，测 K2P。
2. **LOK 的图块位图跨进程传输开销**：共享内存 + 脏矩形的实际帧率未测。→ M0 验证。
3. **parley 在 5 万字单段上的收敛重排是否真能 ≤ 16 ms**：本文的数字来自 cosmic-text 的整块重排（0.34 ms/204 字符），线性外推到 5 万字单段约 80–200 ms，收敛后应大幅下降，但**未实测**。→ M0 必测，这是 P7 的成败点。
4. **LOK 在 Windows 上的最小构建集与包体**：未实测。→ M0。
5. **OV 证书 + 云 HSM 在国内的可获得性与价格**：需询价（DigiCert/Sectigo/GlobalSign 的中国区代理）。→ 采购前确认。
6. **LibreOffice 的中文字体度量与 Word 的差异**：需要 20 份真实文档对照才有结论。→ M3。
7. **「更好的 Excel」用声明式能否覆盖真实需求**：取决于用户要的是「公式栏/快捷键」还是「自绘网格」。→ 需要产品侧的用户访谈，本文无法替代。
8. **插件市场的审核人力**：`verified` 等级需要人工审核，成本未估。→ 运营决策。

## 附录 A：术语

| 术语 | 含义 |
| --- | --- |
| 表面（surface） | 正文区的渲染与输入载体：文本、网格、页面、画布 |
| 引擎（engine） | 某种格式的渲染/编辑实现，运行在 worker 进程 |
| 块（block） | 文档的结构单元（段落、标题、列表项、表格等），是失效传播的单位 |
| 行（line） | 排版结果的一行，是重排计算的单位 |
| 收敛（converge） | 重排到某行时，断行位置与纵坐标与旧结果一致，可停止 |
| capability | 插件可提供或替换的能力名，如 `office.grid` |
| K2P | Key-to-Pixel，按键到像素的延迟 |
| chrome | 应用级界面（标题栏、工具条、状态栏），不含文档内容 |
